# LRN-040 — Récidive du désync reaper (LRN-017) : le fix précédent n'avait corrigé que le payload, pas le suivi

| Pattern observé                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | Contexte                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | Application future                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `spawn_idle_reaper` gardait un `last_emitted: Option<String>` LOCAL (comparant seulement `resolved`), jamais synchronisé avec le suivi de `on_event` (`state.last_emission`, ajouté cette session pour dédoublonner les hooks quasi-simultanés). Dès qu'`on_event` émettait un état via un vrai hook (ex: `Stop` -> `celebrate`), le PROCHAIN tick du reaper (jusqu'à REAPER_INTERVAL=10s après) le trouvait "nouveau" de SON propre point de vue et le réémettait -- un 2e son/bulle "Stop" pour une seule tâche réellement terminée, jamais visible dans des logs consultés juste après le premier Stop. | [LRN-017](LRN-017.md) documentait DÉJÀ ce même anti-pattern (reaper désynchronisé du handler principal) pour un symptôme différent (payload tronqué, badge disparaissant) -- le fix de l'époque avait factorisé la CONSTRUCTION du payload (`resolve_full_state`) mais laissé le SUIVI DE DÉDUPLICATION (`last_emitted`) comme variable locale séparée. Le même angle mort a fini par causer un 2e bug distinct. Fix : le reaper partage maintenant `state.last_emission` (le `Arc<Mutex<...>>` d'`on_event`) au lieu d'un suivi local. | Un process de réémission périodique partageant un point d'émission avec un handler synchrone doit factoriser TOUT ce qui touche à "qu'est-ce qu'on a déjà annoncé" (payload ET suivi de dédup), pas seulement le payload -- une correction partielle de ce pattern laisse la même classe de bug resurgir sous une autre forme. **Méta** : le rituel mémoire (CLAUDE.md) ne grep qu'au tout début de la session sur la 1ère demande -- quand une investigation dérive vers un nouveau sous-domaine en cours de route (ici UI -> bug backend de duplication), re-grepper la mémoire sur les mots-clés du NOUVEAU sujet (ex: `reaper\|duplicate\|emit\|desync`) AVANT de partir en diagnostic empirique aurait fait remonter LRN-017 immédiatement. |
