| Retour intégral (`git restore`) de tout le code touché par la tâche "clic bloqué sur les zones transparentes" -- `src/lib/layout.ts`, `src/lib/windowDrag.ts`, `src/hooks/useAvatarScreenLayout.ts`, `src/components/Avatar.tsx`, `src/components/NotificationBubble/index.tsx`, `src-tauri/src/lib.rs`, `src-tauri/capabilities/default.json` -- à leur état d'avant la tâche (commit `7a0371d`), suppression des fichiers ajoutés (`useAvatarWindowSize.ts`, `useNotificationBubbleContent.ts`). L'app "de base" (fenêtre fixe 480x420, zone morte cliquable inchangée) est restaurée telle quelle. | Après plusieurs itérations toutes insatisfaisantes (cf. [ZBDR-052](../archive/decisions/ZBDR-052.md)/[BDR-053](BDR-053.md)/[ZBLK-026](../archive/blockers/ZBLK-026.md)) -- fenêtre dynamique flashant même avec une commande Rust atomique, puis largeur de bulle restreinte à `avatarSize` révélant un risque réel de texte rogné (mesuré : le message le plus long du pool ne wrappait pas comme attendu à 190px, symptôme d'un bug CSS non diagnostiqué avant l'interruption) -- Baptiste a jugé la situation "catastrophique" et demandé l'abandon complet plutôt qu'une énième itération. Avant de revenir en arrière, recherche demandée explicitement sur un éventuel "mode widget" Tauri : confirmé qu'aucune solution fiable n'existe pour restreindre le hit-test aux seuls pixels peints sur Windows/WebView2 sans chantier d'ingénierie majeur (cf. alternatives). | **`SetWindowRgn`** (région de fenêtre non-rectangulaire, technique historique des widgets type Rainmeter) -- fonctionne bien avec WebView2 pour une forme STATIQUE (cf. [learn.microsoft.com/.../setwindowrgn](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowrgn)), mais écartée pour Hooky : l'avatar est un SVG procédural animé (confettis, bounce, idle...), recalculer/réappliquer une région Win32 à chaque frame (30-60fps) est un chantier d'ingénierie à part entière avec un vrai risque de perf, et les bords d'une région Win32 ne sont JAMAIS anti-aliasés (rendu actuel lissé, dégradation visuelle certaine) -- reste une piste future SI quelqu'un veut l'investir sérieusement, pas un fix. **`SetLayeredWindowAttributes`/`LWA_COLORKEY`** (transparence par couleur-clé) -- écartée : confirmé ne PAS fonctionner dans WinUI 3 (framework composité moderne comme WebView2/DirectComposition, cf. recherche), signal fort d'incompatibilité avec WebView2 par extension. **`WS_EX_TRANSPARENT`** -- déjà la même famille que `setIgnoreCursorEvents` (cf. [LRN-043](../learnings/LRN-043.md)), rend TOUTE la fenêtre traversante uniformément, pas seulement les pixels vides -- aucun apport par rapport à ce qui était déjà confirmé mort. | actif  |
