| Après l'implémentation de la fenêtre dynamique compact/étendue ([BDR-052](../../decisions/BDR-052.md)), déclencher une notification synthétique (curl vers le serveur local) ne redimensionnait pas systématiquement la fenêtre malgré des logs backend confirmant `resolved=celebrate should_emit=true` à chaque fois. Plusieurs fausses pistes explorées avant la vraie cause : un `dragState` bloqué à `true` (hypothèse plausible, corrigée en vrai bug au passage, cf. GLRN-270 -- mais pas la cause de CE symptôme), un souci de permission Tauri (`core:window:allow-set-size`), un `notificationsEnabled` désactivé par erreur (vérifié faux via lecture directe du localStorage WebView2/leveldb). | Deux causes cumulées, découvertes dans l'ordre : (1) l'instrumentation de debug ajoutée pour diagnostiquer n'était jamais rechargée par le HMR de Vite pour un hook non-composant (cf. GLRN-269) -- les tests suivants étaient donc silencieusement invalides ; (2) une fois un redémarrage complet effectué, le mécanisme fonctionnait -- mais restait intermittent tant que le trigger+vérification passaient par PLUSIEURS appels d'outil de la session Claude Code en cours, chacun émettant ses propres hooks réels concurrents (cf. [LRN-060](../../learnings/LRN-060.md)). | Redémarrage complet du process de dev pour retester (élimine la cause 1), puis isolation du trigger+poll dans un seul appel d'outil (élimine la cause 2) -- cycle complet compact→étendu→compact confirmé de façon reproductible. La fenêtre dynamique elle-même a ensuite été abandonnée pour une autre raison (flash constaté en usage réel, cf. [BDR-053](../../decisions/BDR-053.md)), mais ce blocage de vérification était résolu avant cet abandon. | résolu |
